# CruxGPT
#### Video Demo: https://youtu.be/ElfYTIHJ6hU
#### Description:
CRuX GPT is an AI-powered document analysis and retrieval system designed for long-form reference material such as insurance policies, compliance documents, medical coverage plans, and other structured text-heavy files. The user experience is centered around a simple promise: upload a document, ask a question about it, and receive an answer that is grounded in that document rather than a generic large-language-model response. That sounds simple on the surface, but the project does a fair amount of work behind the scenes to make the response trustworthy, traceable, and persistent across sessions.

The project is split into two main parts. The backend is a FastAPI application responsible for authentication, document upload, text parsing, chunking, retrieval, conversation storage, feedback capture, and AI response generation. The frontend is a React application built with Vite that provides the user interface for signing in, uploading documents, chatting with the assistant, browsing conversation history, and submitting suggestions. Taken together, these pieces form a complete full-stack application rather than a single demo script. The frontend is not merely decorative; it is wired directly to the backend APIs and reflects real application state, including login status, document status, and the current user role.

The backend entry point is `backend/app/main.py`. It initializes the database during application startup, configures CORS so the frontend can call the API securely, installs a shared error handler, and mounts the route modules for authentication, users, documents, chat, conversations, feedback, suggestions, and admin features. That file is intentionally small because it acts as the orchestration layer rather than the place where the application logic lives. The real business rules are distributed into services, models, schemas, and the RAG components so each layer has a specific responsibility and the code stays easier to reason about.

The retrieval-augmented generation pipeline lives under `backend/rag/`. The parser reads uploaded files and extracts text from supported formats. The chunker splits that text into smaller passages so the system can search at a more useful granularity than entire documents. The retriever finds the most relevant chunks for a question, and the generator calls Gemini to turn those chunks into a structured answer. The generator is also defensive about model output: if Gemini returns JSON wrapped in code fences or returns a response that cannot be parsed cleanly, the code falls back to a safe response instead of crashing. This matters because the user should still receive a usable result even when the model response is imperfect.

The chat orchestration happens in `backend/services/chat_service.py`. That service creates or reuses a conversation, loads a bounded amount of recent history, saves the user’s latest message before generation so nothing is lost if downstream work fails, performs retrieval against the current user’s document set, and stores the assistant’s response along with source metadata. It also auto-titles a new conversation from the first message, which makes the conversation history more readable in the UI. This service is the heart of the app because it connects the retrieval layer, the persistence layer, and the model generation layer into one user-facing flow.

The data model is organized under `backend/models/` and the request and response contracts live in `backend/schemas/`. I kept those concerns separate on purpose. The models describe how the data is stored, while the schemas describe what the API accepts and returns. That separation makes the project easier to extend and easier to test because the database structure is not mixed with user-facing payload shapes. The service layer under `backend/services/` keeps the route handlers thin, which reduces duplication and makes the application logic easier to reuse across endpoints. The backend test suite under `backend/tests/` exercises the important behaviors, including authentication, chat, and document workflows, so the project is not relying purely on manual testing.

On the frontend, `frontend/src/App.jsx` is the top-level composition point. It decides whether to show the main pages or the admin dashboard depending on the authenticated user role. `frontend/src/contexts/AuthContext.jsx` manages login state and always resolves the current role from the backend’s verified `/api/auth/me` response instead of trusting anything stored locally. That choice matters because a front end should never be the source of truth for authorization. `frontend/src/services/api.js` is the centralized API client, which attaches access tokens, refreshes expired sessions, and normalizes backend error responses into a consistent JavaScript error shape. Centralizing those concerns avoids repeating request logic across components and keeps the app behavior predictable.

The main chat experience is implemented in `frontend/src/components/Chat.jsx`. That component is responsible for the user’s message input, the assistant message stream, document attachment, upload validation, polling for indexing status, feedback submission, and conversation hydration when opening an existing chat. Users can attach PDFs, DOCX files, and plain text files, but the UI checks the file type and size before uploading to reduce unnecessary backend errors. Once a document is uploaded, the interface shows it moving through upload and processing states until it becomes ready. That small state machine is important because it gives the user immediate feedback and makes the indexing process feel visible instead of mysterious.

Supporting UI pieces such as `AuthModal`, `AdminView`, `Layout`, `Header`, `Footer`, and the page components under `frontend/src/pages/` provide the rest of the product shell. The app is not trying to be visually minimal at the expense of clarity; instead it tries to feel like a polished product while still making the document workflow obvious. There are also supporting screens for things like problem statements, challenges, profiles, and contact or suggestion flows, which make the app feel complete rather than one-dimensional.

I made a few deliberate design choices to keep the project practical and trustworthy. First, the assistant is grounded in retrieved document chunks so the answer can cite the source material instead of inventing a response. Second, the frontend does not store a fake role locally; it asks the backend for the current authenticated user and uses that server-side truth to decide what to render. Third, the API client is centralized so token handling, retries, and error parsing are consistent everywhere. Fourth, uploaded files are validated in the UI before the request is sent, which improves the user experience and reduces avoidable server work. Fifth, conversation history is persisted so a user can come back later and continue where they left off instead of starting from scratch.

The project also includes workflows beyond basic question answering. Users can revisit earlier conversations, inspect source passages used in the answer, and submit thumbs-up or thumbs-down feedback. That feedback is stored in the backend and is useful both as a product feature and as a signal for future improvement. The suggestion form provides a direct path for users to report issues or propose new functionality, and the admin view supports a higher-level operational role without exposing those controls to ordinary accounts. These additions matter because they make the system feel like an application with multiple user journeys instead of a single chatbot interface.

Another important design detail is isolation. Documents, chunks, conversations, and messages are scoped to the authenticated user on the server side, so one user cannot retrieve another user’s uploaded material. That makes the retrieval system safer and more realistic for a multi-user environment. It also means the project demonstrates a proper access-control story instead of just a search-and-answer prototype. In practice, that separation is a large part of what turns a basic RAG demo into an actual product.

Overall, CRuX GPT is intended to show a full-stack application with authentication, document processing, retrieval-augmented generation, persistence, and a polished interface. The codebase is organized so the backend, frontend, and data layer each have a clear responsibility, and the behavior is visible through the UI rather than hidden behind a single prompt box. The project aims to be useful in realistic reference-document scenarios while also showing enough technical depth to demonstrate thoughtful engineering decisions.
